# UI 描述统一架构

源码扫描形成的场景知识和根据 PRD 生成的 UI 描述使用同一套设计语言。输出顺序固定为“为什么存在 → 页面全貌 → 布局骨架 → 区域 → 组件实例 → 流程与状态”，不得从零散组件直接开始。

## 一、两层主知识与一层实例证据

### 1. 组件能力

组件知识描述设计语义中的能力类型，不记录工程实现名。每个组件至少说明：

- 解决什么交互问题。
- 适用于什么用户目标、对象规模、任务阶段和风险条件。
- 什么情况下不应使用，应换成什么能力。
- 在不同场景中承担什么角色，是必需、条件出现还是不建议出现。
- 与其他组件怎样组合、谁先谁后、谁控制谁、谁反馈谁。
- 内容、布局、交互和状态规则。
- 哪些来源项目和证据支持这些观察。

组件不能脱离场景成为孤立清单。源码中同名组件的存在不能证明它只有一种设计语义；多个工程组件也可能归入同一种设计能力。

### 2. 场景配方

场景是跨项目复用的主知识，负责把用户任务转换为页面形态、区域骨架和组件搭配。每个场景至少说明：

- 用户目标、对象范围、任务阶段、时长、风险和结果方式。
- 适用与不适用边界。
- 推荐页面形态、主次布局、区域顺序和选择理由。
- 必需组件、条件组件和应避免组件的角色、位置、条件与理由。
- 用户任务顺序、关键状态、前后场景和设计边界。
- 跨项目变体、真实案例摘要和证据来源。

场景不能按标题归并。只有语义画像一致时才复用同一场景；稳定差异形成限定变体，冲突进入待确认。

### 3. 项目页面实例

页面实例只保存在隐藏事实源，用于记录某个来源项目中多个场景怎样组合。它不是第三套规范，也不生成独立 `页面/` 正文。

页面实例保留完整观察：

1. 页面定位：来源项目、业务模块、入口、用户目标和关联场景。
2. 页面全景：应用外壳、导航、内容画布、滚动与覆盖层。
3. 布局骨架：主次区域、区域顺序、对齐、空间占用和固定/流动关系。
4. 区域明细：位置、目的、优先级、内部布局和相邻关系。
5. 组件实例：业务角色、内容、位置、伸缩、交互、出现条件和局部状态。
6. 任务流程、页面状态、适配规则、覆盖盲区和证据。

页面实例为场景提供两种价值：证明某种组合真实出现过，或揭示某个项目的限定变体。它不能自动成为新页面的标准答案。

## 二、从多个项目积累知识

同一知识库可以先扫描 A，再扫描 B。归并顺序为：

1. 将新项目观察写成带来源的组件观察和页面实例。
2. 用用户目标、对象范围、阶段、时长、风险、结果和组件角色匹配现有场景。
3. 语义相同则追加项目来源、证据和实例；不复制场景正文。
4. 主任务相同但条件差异稳定时创建场景变体。
5. 同一条件下冲突时并列保留并建立待确认项。
6. 实质不同才创建新场景或新组件能力。

跨项目出现次数可以提高证据广度，但知识状态仍由 `observed/candidate/normative/exception/hypothesis` 单独决定。

## 三、组件命名边界

可见文档可以使用设计师能理解的中文组件类型，例如“页面标题”“条件输入”“结果列表”“状态标签”“主要行动”“分页导航”“确认对话框”和“侧向详情区”。不得出现源码组件名、属性、事件、文件路径、框架术语或代码片段。

组件描述必须包含业务角色，不能只写“这里有一个按钮”或“这里放一个表格”。推荐写法是：“结果区右上方的页面级主要行动，用于创建新对象；仅在用户具备创建权限时出现。”

## 四、尺寸与视觉证据

- 源码或运行页面能确认的宽度、间距、对齐、栅格、固定方式和响应式阈值，可以作为页面实例观察记录。
- 相同规律在多个项目中出现时，可以归纳为候选场景规则，但必须保留来源和适用条件。
- 无法确认的具体像素、颜色、字号和品牌样式不得猜测，写为“未确认”。
- 运行页面观察和源码规则冲突时并列保留，不静默覆盖。
- 出现次数只能提高常见程度和证据广度，不能自动升级为正式规范。

## 五、PRD 生成顺序

根据 PRD 生成 UI 描述时按以下顺序推导：

1. 归一化用户目标、对象范围、任务阶段、上下文、时长、风险、结果、权限和异常。
2. 选择一个主场景，补充必要的前置、辅助、反馈和恢复场景。
3. 合并场景组件配方，处理重复、条件和冲突。
4. 使用主场景的页面形态和布局骨架，把组件分配到有明确目的的区域。
5. 按需读取 1–3 个跨项目页面实例，校准外壳、空间关系、状态与限定变体。
6. 生成新的页面描述；不要把任何历史页面实例直接复制成规范答案。
7. 补全任务流、状态变化、适配规则、设计边界和待确认项。

PRD 回答使用以下固定标题；证据不足时保留标题并写明未知：

1. `需求与场景判断`
2. `页面全景`
3. `布局骨架`
4. `区域与组件搭配`
5. `组件使用明细`
6. `任务流程`
7. `关键状态`
8. `适配、边界与待确认`

## 六、完整性检查

一份合格的场景规范或 PRD UI 描述应能回答：

- 不看源码时，设计师能否画出页面的大致骨架？
- 能否区分应用导航、页面内容、主任务区域和辅助区域？
- 每个组件是否有业务角色、位置和出现条件？
- 组件搭配能否回到明确任务场景？
- 初始、加载、空、失败、权限受限、部分成功等状态是否说明区域级变化？
- 使用的历史页面经验是否保留来源，并与正式规范区分？
- 未确认的尺寸、视觉或运行行为是否明确标出？

任一答案为“不能”时，描述仍不完整。
