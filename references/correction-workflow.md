# 受控更正工作流

## 变化分类

| 类型 | 含义 | 可以影响什么 |
|---|---|---|
| 观察事实修正 | 之前对某来源项目或页面实例的理解有误 | 页面实例、观察摘要、证据关系、候选归纳 |
| 设计规范 | 团队明确以后应如何设计 | 规范规则和后续 PRD 推断 |
| 限定例外 | 一般规则在明确条件下不适用 | 例外范围内的选择 |
| 待验证想法 | 暂时值得记录但未确认 | 待确认项，不参与强约束 |

同一句话可能包含多类变化，应拆成多个提案条目。例如“历史页面其实不是弹层，以后也不应该用弹层”同时包含事实修正和规范决定。

## 影响图

从目标对象向外检查：

1. `relations` 直接相连的前后场景。
2. 引用目标组件的场景配方、组合组件和带来源的页面实例。
3. 同一分类中适用条件重叠的场景。
4. 共享同一页面形态的场景与页面实例。
5. 贡献该结论的来源项目、场景变体和业务模块。
6. 约束目标对象的通用规则与限定例外。
7. 依赖该结论的待确认项和现有冲突。

影响集不是“全部知识库”。只展开直接关系和一跳共享约束；发现新的实质依赖时再扩一跳。

## 冲突判定

- 两条规则在相同条件下给出互斥页面形态。
- 新规则扩大适用范围后吞掉已有场景或例外。
- 修改主场景后，前后任务流无法衔接。
- 场景页面骨架变化后缺失原有关键状态，或页面实例修正没有回写受影响的候选归纳。
- 组件适用条件变化后，场景配方仍把它列为无条件必需。
- 组件或区域位置变化后，场景页面骨架或相关页面实例中的主次、顺序、控制/反馈关系断裂。
- 声称修正来源项目事实却没有新证据，或用偏好覆盖页面实例观察。
- 删除某来源项目后仍保留只由该项目支持的候选规则。
- 把多个项目的重复实现直接升级为正式规范。
- 新例外没有可判断的进入条件或退出条件。

冲突处理方式只有三种：缩小适用条件、声明优先级明确的例外、保留冲突进入待确认。不得静默删除旧规则。

## 预览模板

```text
更正类型：
目标知识：
当前内容：
建议内容：
适用范围：
不影响的内容：
关联场景：
冲突检查：
证据与可信度变化：
预计 revision：
```

用户的“好”“可以”“改吧”只有在紧接着该预览且无新条件时才算确认；如果用户补充了范围或例外，应重做预览。

## 提交规则

- 候选知识的 `revision` 必须等于当前版本加一。
- 变更记录的 `baseRevision` 必须等于当前版本。
- 变更记录必须是已确认状态，并列出目标与影响对象。
- 删除来源、知识对象或证据时，精确 ID 必须同时列入 `targets` 与 `allowRemovals`；未声明删除由提交器拒绝。
- 先完整校验候选，再替换事实源、追加历史、生成派生视图。
- 新增证据时提交完整候选证据文件；任一步失败都不得留下半个新版本或孤儿证据。
