# 查询工作流

## 需求归一化

先把 PRD 转成设计决策问题，不急于匹配页面：

| 维度 | 要回答的问题 |
|---|---|
| 用户目标 | 用户最终要得到什么结果？ |
| 对象范围 | 单个对象、对象集合还是跨对象汇总？ |
| 任务阶段 | 查找、理解、输入、判断、执行、追踪还是恢复？ |
| 上下文 | 是否必须看着上游信息完成任务？ |
| 时长 | 即时完成还是离开后继续？ |
| 风险 | 是否不可逆、影响范围大或需要依据？ |
| 结果 | 单一成功、部分成功、排队还是可恢复失败？ |
| 权限 | 谁能看、谁能做、限制如何解释？ |

## 组合规则

- 先选择承担主要用户目标的主场景，再补充前置查找、对象理解、确认、结果反馈等辅场景。
- 主场景决定页面大结构，辅场景决定局部区域和状态，不把每个小动作都升级为独立页面。
- 当任务需要保持上游上下文且内容短时，优先在当前页面展开辅助任务；内容长、风险高、阶段多或需要稳定返回入口时，使用独立任务空间。
- 长时间处理不能只显示提交反馈，还要能再次找到任务、理解进度和处理失败对象。
- 知识库没有覆盖的新场景可由多个已知场景组合推断，但必须标为推断。

## 从场景生成组件搭配

1. 先确定一个承担主要目标的主场景，主场景决定页面形态、主要区域和必需组件。
2. 辅场景只补充前置、依据、反馈或恢复能力，不能无条件引入整套组件。
3. 合并场景配方时，先放入必需组件，再逐项判断条件组件；命中避免规则或条件冲突时不放入，并说明原因。
4. 同一组件被多个场景选择时合并为一个实例，但保留它承担的多个业务角色。
5. 组件需要被分配到有明确目的的页面区域；无法确定位置时标为待确认，不能生成悬空组件清单。
6. 按需读取来自不同项目的真实页面实例，校准应用外壳、主次布局、区域顺序、空间占用和状态变化；实例只是带来源的观察证据，不自动成为新 PRD 的正式标准。

## 页面描述输出

最终回答必须遵循 [UI 描述统一架构](ui-description-architecture.md) 的八个固定标题，从页面全景写到组件实例。它是根据场景生成的新页面描述，不是知识库中的平级“页面规范”。关键状态必须说明“什么触发、哪些区域或组件变化、保留什么上下文、如何恢复”，不能只列状态名称。

## 可信度

推荐顺序为：限定条件匹配的正式规范 > 多项目证据候选 > 单项目候选 > 单一页面实例观察 > 相似场景推断。多项目重复不会自动成为正式规范；高层通用规则与限定例外冲突时，先检查是否命中例外范围。

回答中不必展示内部 ID 和证据定位；只有用户询问来源或存在争议时才解释证据等级。
