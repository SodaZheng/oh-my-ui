# 查询 UI 知识库

先完整阅读 [共同知识契约](../../references/knowledge-contract.md)、[UI 描述统一架构](../../references/ui-description-architecture.md) 和 [查询工作流](../../references/query-workflow.md)。本 Skill 永远只读；用户在问题里顺带提出更正时，先回答可回答部分，再建议切换到 `$correct-ui-knowledge`。

## 检索顺序

1. 定位 `knowledgeRoot` 下的 `doc/ui/UI设计知识库/00-知识库导航.md` 与 `doc/ui/.ui-knowledge/knowledge.json`。两者缺一时说明知识库不完整；不得把当前业务项目目录误当成统一知识库，也不得回退读取旧 schema 路径。
2. 从需求中提取：用户目标、对象范围、任务阶段、处理时长、风险、结果方式、权限角色、入口和异常状态。缺失项保持未知。
3. 先读导航和场景摘要，只选择一个主场景及最多 2–5 个辅助场景；再读取这些场景的组件配方。
4. 合并必需组件和命中条件的组件，排除不满足条件或处于避免规则中的组件；发现配方冲突时保留条件，不擅自堆叠。
5. 从 `pageInstances` 读取最相近的 1–3 个真实页面实例，优先选择不同来源项目，校准外壳、布局、区域关系和状态经验；实例只作为带来源观察，不直接复制为答案。
6. 读取被选组件的完整规范，并检查通用规则、页面形态、跨项目变体、例外、冲突和待确认事项。
7. 如果没有直接命中，用相近场景和组件配方组合做“推断”，明确写出推断依据和缺失信息，不把推断写回知识库。

## 回答格式

使用中文设计语言，严格按 [UI 描述统一架构](../../references/ui-description-architecture.md) 的八个标题输出：

1. 需求与场景判断。
2. 页面全景。
3. 布局骨架。
4. 区域与组件搭配。
5. 组件使用明细。
6. 任务流程。
7. 关键状态。
8. 适配、边界与待确认。

描述必须从场景给出的页面全貌逐层进入区域和组件。每个组件实例写清业务角色、位置、空间方式、内容、交互、出现条件和局部状态；不能只列组件名称。知识不足时保留对应标题并明确“未确认”，不得靠通用 UI 经验静默补全。

不得向设计师暴露工程组件名、属性、文件路径、路由实现、框架术语或代码。可以引用场景中文标题，不输出内部对象结构。

## 大知识库控制

- 不整份加载 `knowledge.json`；先用导航、标题检索和局部 JSON 查询定位。
- 场景超过 6 个时分两轮：候选摘要筛选，然后只展开最高相关项。
- 页面实例按场景、页面形态和来源项目筛选；默认最多读取 3 个，不因实例数量多而提高规范等级。
- 同一结论有冲突时并列呈现适用条件，不擅自消解。
- 回答结束后确认没有产生任何文件修改。
