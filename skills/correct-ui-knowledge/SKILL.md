# 更正 UI 知识库

开始前完整阅读：

- [共同知识契约](../../references/knowledge-contract.md)
- [UI 描述统一架构](../../references/ui-description-architecture.md)
- [受控更正工作流](../../references/correction-workflow.md)
- [质量门槛](../../references/quality-gates.md)

## 核心原则

- 自然语言反馈不是直接写入指令，先转成结构化更正提案。
- 区分四类变化：观察事实修正、设计规范、限定例外、待验证想法。
- 修改一个来源项目、组件、场景或页面实例前必须检查相关组件配方、场景变体、页面实例、上位通用规则、来源索引和待确认事项。
- 设计偏好不能改写为“历史页面事实”；源码观察也不能自动升级为正式规范。
- 多项目重复不能自动升级为正式规范；删除或修正来源项目时要重新评估只由它支持的候选知识。
- 语义变化必须先预览、再由用户明确确认。纯错别字或格式修复可直接处理，但不得改变适用边界和含义。

## 第一阶段：提案与影响分析

1. 只定位 `knowledgeRoot` 下的 `doc/ui/.ui-knowledge/knowledge.json` 与 `doc/ui/UI设计知识库/`，读取当前 `revision`、来源项目、导航、目标组件/场景/页面实例和直接关系；不得修改被扫描的 `sourceRoot`，也不得读取旧 schema 路径。
2. 将反馈解析为：变化类型、目标对象、原内容、新内容、理由、适用条件、例外范围、证据来源和置信度。
3. 建立影响集：贡献该结论的来源项目、引用组件的场景配方和页面实例、场景变体、直接关系场景、共享页面形态、关联通用规则和待确认项。
4. 检查至少十类冲突：适用条件重叠、组件组合互斥、组件位置冲突、页面形态不一致、区域层级断裂、状态遗漏、例外范围不清、观察与规范混淆、来源被移除后证据悬空、同义场景错误拆分或合并。
5. 向用户给出中文预览：将修改什么、不会修改什么、受影响范围、发现的冲突、建议处理方式和新版本号。
6. 暂停，等待用户明确表达确认、调整或取消。未确认不得改动语义知识。

## 第二阶段：确认后提交

1. 重新读取当前 `revision`。若与预览版本不同，判定为并发变化，重新做影响分析。
2. 在临时位置生成完整候选 `knowledge.json` 和变更记录；不得只做不可追踪的局部文本替换。需要删除对象或证据时，必须把精确 ID 同时列入 `targets` 与 `allowRemovals`，且只能使用用户已确认的删除范围。
3. 保留稳定 ID、未知字段、未涉及来源项目、历史证据和原始页面实例；更新场景与实例双向引用及所有派生索引。
4. 若新增或修正证据，同时生成包含全部既有证据的候选 `evidence.jsonl`；用 `node <插件根目录>/scripts/commit-kb.mjs <knowledgeRoot> <候选知识文件> <变更记录文件> [候选证据文件]` 校验并提交。不得预先改正式证据文件。脚本路径相对于本文件向上两级。
5. 重新生成可见文档并运行最终校验。失败时保持旧版本不变，报告失败原因。
6. 告知用户实际变更、冲突处理结果、新 revision 和仍待确认的事项。

## 更正提案最小字段

```json
{
  "id": "CR-YYYYMMDD-NNN",
  "baseRevision": 1,
  "type": "observation-correction | normative-rule | scoped-exception | hypothesis",
  "summary": "中文变化摘要",
  "targets": ["稳定对象 ID"],
  "impactIds": ["受影响对象 ID"],
  "conflicts": [],
  "decision": "confirmed",
  "reason": "用户确认的理由"
}
```

不要把敏感凭证、完整源码、用户会话或无关工程细节写入变更记录。
