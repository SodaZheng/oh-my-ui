# 扫描前端并增量构建统一 UI 知识库

开始前完整阅读：

- [共同知识契约](../../references/knowledge-contract.md)
- [UI 描述统一架构](../../references/ui-description-architecture.md)
- [扫描建库工作流](../../references/build-workflow.md)
- [质量门槛](../../references/quality-gates.md)

## 工作边界

- 产出使用中文设计语言；可见文档不得出现工程组件名、属性、源码路径、框架术语、内部 ID 或代码。
- 组件能力与场景配方是可复用主知识；真实页面只保存为带来源的 `pageInstances`，不得生成平级 `页面/` 规范。
- 历史实现是观察证据，不自动成为正式规范；多个项目重复只能提高证据广度。
- 不确定内容进入待确认；跨项目冲突不得静默覆盖。
- 登录由用户控制；不得索取、保存或绕过凭证、验证码、权限或风控。
- 脚本只负责初始化、迁移、格式化、校验和原子提交；页面语义与场景归并由 Agent 判断。

## 执行顺序

1. 明确 `sourceRoot` 和 `knowledgeRoot`。前者是本次扫描项目，后者是持续累计的统一知识库；两者未明确但当前目录已存在知识库时，将当前目录作为 `knowledgeRoot`，仍要从用户指定或可发现的项目确定 `sourceRoot`。两者相同或嵌套时，从源码扫描中排除 `<knowledgeRoot>/doc/ui/`，避免循环吸收派生知识。
2. 定位 `<knowledgeRoot>/doc/ui/.ui-knowledge/knowledge.json`。不存在时运行 `node <插件根>/scripts/init-kb.mjs <knowledgeRoot>`；schema 为 1.1.0 时先运行 `migrate-kb.mjs <knowledgeRoot> --source-root <sourceRoot>`。不得覆盖另一份事实源。
3. 运行 `node <插件根>/scripts/derive-source-key.mjs <sourceRoot> [--id <明确项目ID>]`，再在 `sourceProjects` 中定位当前项目。匹配顺序是明确 `PRJ-` ID > `identity.stableKey` > 仓库远端与清单名称 > 入口/模块画像；本地路径只作为别名。工具返回 `ambiguous` 或多个候选无法区分时让用户确认。首次扫描时登记稳定身份、项目画像、未知项和空扫描账本；增量补扫或路径移动时复用原 ID。
4. 建立当前项目的路由账本与组件账本。扫描单位分别是“入口 × 布局链 × 任务状态 × 角色/权限 × 进入方式”和“实现身份 × 真实调用族 × 任务场景 × 状态/变体”。
5. 每次追踪一个扫描单位：入口 → 外壳 → 布局 → 区域树 → 组件实例 → 样式和空间 → 状态/权限 → 覆盖层 → 后续任务。把完整组合写成带 `sourceProjectId` 的页面实例。
6. 先归并组件能力，再为页面实例提取场景语义画像：用户目标、对象范围、任务阶段、时长、风险、结果和组件角色。
7. 与全库候选比较：语义相同则追加来源/证据/实例；主任务相同且差异有条件则追加场景变体；同条件冲突则并列保留并建立待确认；实质不同才创建新场景。
8. 把可复用页面信息写入场景的 `pagePattern`：页面形态、布局骨架、区域顺序和关系。不要把具体项目壳层或品牌差异写成通用规则。
9. 生成完整候选 `knowledge.json`、候选 `evidence.jsonl` 和 `type: source-scan` 变更记录。候选证据必须包含全部既有证据和本次新增证据，变更记录必须声明本次 `sourceProjectIds`。用 `commit-kb.mjs <knowledgeRoot> <candidate> <record> <candidate-evidence>` 原子提交；不得预先追加正式证据。
10. 重新渲染并运行 `validate-kb.mjs <knowledgeRoot>`。确认可见目录没有 `页面/`，场景与页面实例双向引用一致。

## 归并判定

不要按标题、路由、项目名或工程组件名去重。依次比较：

1. 用户最终目标。
2. 单对象、集合或跨对象范围。
3. 查找、理解、输入、判断、执行、追踪或恢复阶段。
4. 即时或长时间处理。
5. 风险、可逆性和影响范围。
6. 单一成功、部分成功、排队或恢复结果。
7. 组件承担的业务角色及区域关系。

`semanticKey` 必须唯一并保持稳定。证据不足以判断时，保留独立观察并建立待确认项，不要强制合并。

## 上下文控制

- 顺序使用：全库轻量索引 → 当前来源项目画像 → 单个扫描项 → 直接依赖 → 相关场景候选 → 按需实例与证据。
- 不一次读取全仓库、全部页面实例或全部证据。
- 每完成一批扫描项就写检查点；工作上下文以约 160k 为软上限，至少保留 30% 用于归并和冲突检查。

## 完成条件

- 当前来源项目路由与组件账本有完整分母和终态。
- 新增页面实例保留来源、多个关联场景、完整结构、状态、适配和覆盖。
- 组件与场景均保留来源项目和证据。
- 同义场景已归并，稳定差异形成变体，冲突进入待确认。
- 跨项目重复没有自动升级为正式规范。
- B 项目提交没有删除或修改作用域外 A 项目的画像、页面实例和证据。
- 可见目录以场景为主，不存在独立页面规范。
- 所有确定性校验通过，并报告当前项目覆盖、全库变化和仍待确认项。
