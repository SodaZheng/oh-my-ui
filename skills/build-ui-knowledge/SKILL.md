# 扫描前端生成 UI 知识库

以 Agent 理解为主、确定性脚本为辅。先理解项目如何组织页面，再从路由与真实任务状态逐页追踪；不要假设任何框架、路由库或组件体系。

开始前完整阅读：

- [共同知识契约](../../references/knowledge-contract.md)
- [UI 描述统一架构](../../references/ui-description-architecture.md)
- [扫描建库工作流](../../references/build-workflow.md)
- [质量门槛](../../references/quality-gates.md)

## 工作边界

- 产出必须是中文、设计师语言。
- 可见文档不得出现组件实现名、属性名、源码路径、框架术语或代码片段。
- 关注“用户在什么场景完成什么任务、设计组件为何出现、页面如何从大到小组织、状态如何变化”。可以整理中文设计组件能力，不能输出工程组件清单。
- 历史实现是观察证据，不自动等于正式设计规范。
- 不确定内容进入待确认事项，不得补全成事实。
- 脚本只能初始化、格式化、校验和原子提交，不能替 Agent 判断页面语义。

## 执行顺序

1. 确认扫描根目录、固定知识库目录 `doc/ui/` 和是否增量更新。`init` 只创建空结构，不得预置场景、场景分组、组件、页面形态或页面蓝图。若项目根目录存在旧版 `UI设计知识库/` 或 `.ui-knowledge/`，不得读取、合并或另建第二套知识库；先报告旧路径并让用户确认迁移。若目录中没有可识别的前端源码，停止并说明缺少什么，不生成虚构知识。
2. 建立项目画像：入口、路由来源、布局层、状态来源、权限分支、异步边界、覆盖层和可运行方式。记录已确认项与未知项。
3. 同时建立路由账本和组件账本。路由扫描单位是“路由 × 布局链 × 任务状态 × 角色/权限 × 进入方式”；组件账本记录真实调用场景、内容、位置、组合、状态和样式来源，不按组件定义文件直接宣布设计规范。
4. 每次只追踪一个扫描单位：路由声明 → 页面入口 → 应用外壳 → 布局链 → 区域树 → 组件实例 → 样式与空间关系 → 状态与权限分支 → 覆盖层 → 后续任务入口。为页面全景、布局、组件、状态和适配分别保存证据与覆盖状态。
5. 在跨路由聚合前先写检查点。先把源码组件用法归纳为中文“组件能力”，再从真实页面任务生成场景和场景分组，将相同用户目标、适用条件、页面形态和状态组合归并为“场景配方”，最后保留每个真实页面的详细“页面蓝图”。不要套用内置场景分类，也不要按工程组件名归并。
6. 必要时运行页面核对结构。登录必须由用户控制；不得索取、保存或绕过凭证、验证码、权限或风控。
7. 写入隐藏事实源，生成可见中文文档，再执行结构、引用、语言和冲突校验。

## 256k 上下文控制

- 顺序固定为：项目索引 → 单个路由摘要 → 直接依赖 → 必要状态分支 → 按需证据。
- 不一次读取全仓库、全部页面或全部证据。
- 单次工作集只保留一个路由及其直接任务链；完成后把结论写入 `scanState` 再继续。
- 工作上下文以约 160k 为软上限，至少保留 30% 用于汇总、冲突检查和最终生成。
- 长文件先检索符号和调用点，再读取相关片段。跨路由共用抽象只分析一次，其他路由引用其结论。
- 每处理一批路由都重新读取轻量索引，不依赖聊天记忆保存全量状态。

## 产出结构

在被扫描项目的 `doc/ui/` 目录生成：

```text
doc/ui/
├── UI设计知识库/
│   ├── 00-知识库导航.md
│   ├── 01-通用设计规则.md
│   ├── 页面/
│   ├── 场景/
│   ├── 组件/
│   ├── 02-页面形态索引.md
│   ├── 03-业务模块索引.md
│   ├── 04-组件使用规范索引.md
│   └── 99-待确认事项.md
└── .ui-knowledge/
    ├── knowledge.json
    ├── evidence.jsonl
    └── changes.jsonl
```

用 `node <插件根目录>/scripts/init-kb.mjs <项目根目录>` 安全初始化；已有知识库默认不得覆盖。完成结构化知识后运行 `render-kb.mjs` 和 `validate-kb.mjs`。脚本路径相对于本文件向上两级。

## 完成条件

- 路由账本中的每个扫描单位都有完成、待核对或明确排除状态。
- 组件账本中的每个调用族都有完成、待核对或明确排除状态，并报告独立覆盖分母。
- 每个正式结论都能回到证据；只有单一弱证据的内容保持候选状态。
- 每个组件规范都说明适用/禁用场景、场景角色、组合关系、内容、布局、交互和状态规则。
- 每个场景都包含必需、条件和避免组件配方，且每项有角色、位置、条件与理由。
- 每个页面蓝图从应用外壳、布局骨架、区域树写到组件实例，并包含任务流、区域级状态变化和空间适配。
- 场景之间的适用边界、例外和冲突已检查。
- 可见目录可让设计师从任务场景进入，不需要理解内部数据结构。
- 校验命令全部通过，并报告覆盖范围、盲区和待确认项。
